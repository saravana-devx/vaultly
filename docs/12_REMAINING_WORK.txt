E. INTERVIEW / RESUME PROJECT - SHOULD YOU SHOW IT?
---------------------------------------------------
SHORT ANSWER: Yes, show it - but only after you can explain it, and be honest about how it
was built.

Why it is worth showing
  - It is a real, working system (auth, encryption, Kafka, Redis, Postgres, React, Docker),
    not a tutorial clone.
  - It gives you concrete things to talk about: envelope encryption, a Redis+Lua rate limiter,
    a Kafka audit pipeline with a fallback, per-environment RBAC, dynamic DB credentials.
  - It has tests (36 Go tests), CI and written docs, which most
    student/portfolio projects do not.

Show it ONLY IF you can do all of these
  [ ] Run it from scratch on your machine (docker compose up) without help.
  [ ] Explain, without notes: how a secret is encrypted, how the rate limiter works, how an
      audit event travels through Kafka, how a service token is checked.
  [ ] Make one small change live (e.g. add a field to a secret, or a new rate-limit rule) and
      show it works. Interviewers often ask this to confirm you understand the code.
  [ ] Answer "what would you improve?" using section K of 04_LOW_LEVEL_DESIGN.txt.
  If you cannot yet, spend a few days on docs 02-04 first. Showing a project you cannot explain
  hurts you more than not showing one.

Be honest about AI assistance
  - This project was built with an AI coding assistant. If you are asked who wrote it or how,
    say so plainly: "I designed the features and made the decisions, and used an AI assistant
    to speed up implementation. I've read and tested it and can walk you through any part."
  - Do NOT say you personally typed every line. Being caught overstating is the real risk;
    using AI tools is normal and many teams expect it.
  - Only claim what you can defend. Use the "THINGS NOT TO CLAIM" list in
    11_RESUME_AND_INTERVIEW_GUIDE.txt.

How to present it
  - Resume: one project entry + the GitHub link (bullets are in file 11).
  - GitHub: README with 3-4 screenshots and a short demo video/GIF at the top; docs/ folder
    visible. Pin the repo.
  - In the interview: offer a 5-minute demo first (script in file 11), go into code only when
    asked. Lead with your 2-3 strongest points and mention the weaknesses yourself before they do.
  - Before publishing screenshots, remove anything personal (your email address in the sidebar
    or members list) and make sure no real credentials appear. The seeded keys are fake.

Do NOT show it if
  - It contains real secrets, real customer/employer data, or your real .env (keep .env out of git).
  - An employer's rules forbid AI-assisted work for the role/assessment you are applying to.
