13 - OPENBAO KEY SERVICE AND PERSONAL-DATA ENCRYPTION
=====================================================
Two related upgrades that harden the root of trust and protect personal data.

PART 1 - OPENBAO AS THE KEY SERVICE
-----------------------------------
What changed
  Before: one MASTER_KEY in an environment variable wrapped every project key.
  Now:    the wrapping key lives INSIDE OpenBao (the open-source fork of HashiCorp Vault).
          Vaultly only asks OpenBao to "wrap this data key" / "unwrap this data key".
          The root key never leaves OpenBao and is never in Vaultly's memory or config.

What did NOT change
  Secret values are still encrypted locally with AES-256-GCM using the per-project key.
  OpenBao is used only for the small key-wrapping calls, so reading a secret does not
  call OpenBao for every value (see "DEK cache" below).

How the pieces fit
  internal/crypto/provider  KeyProvider interface: NewDEK / UnwrapDEK / Rewrap
     Local    MASTER_KEY from the environment (the old behaviour, still supported)
     Transit  OpenBao Transit engine over HTTP (datakey, decrypt, encrypt, rewrap)
     Hybrid   OpenBao for everything new, plus READ-ONLY use of the old MASTER_KEY for keys
              that have not been migrated yet
  cmd/server/keys.go        picks the provider from KEY_PROVIDER, waits for OpenBao to be ready,
                            starts the token renewer, and implements `server rewrap`
  openbao/bootstrap.sh      sidecar: initialise (first time), unseal (every restart), enable
                            Transit, create key "vaultly", least-privilege policy, app token

Why Transit data keys ("envelope encryption with an external KMS")
  A DEK is generated by OpenBao (datakey/plaintext). You get the plaintext once (used in memory)
  plus a wrapped copy ("vault:v1:...") that is stored in projects.encrypted_dek. To use the key
  later, Vaultly sends the wrapped copy back to OpenBao to be unwrapped. Rotating the OpenBao
  key = `rewrap` (OpenBao re-wraps the stored copies; the DEKs themselves do not change, so no
  secret has to be re-encrypted).

Least privilege
  The app token can ONLY update four paths: transit/datakey|encrypt|decrypt|rewrap for the key
  "vaultly" (policy vaultly-app). It cannot read the key, list keys, or touch other engines.
  The transit key is non-exportable. A live test proves the token is refused for any other key.
  The token is "periodic" (768 h) and renewed hourly by the backend; the bootstrap sidecar
  re-issues it if it is ever invalid.

DEK cache
  Unwrapping needs a network call, so unwrapped project keys are cached in memory for
  KEY_CACHE_TTL_SECONDS (default 60; 0 disables). Trade-off: plaintext keys sit in RAM a little
  longer in exchange for speed and for surviving short OpenBao outages.

Configuration (backend environment)
  KEY_PROVIDER          local | openbao        (docker-compose.yml defaults to openbao)
  BAO_ADDR              http://openbao:8200
  BAO_TOKEN_FILE        /token/app-token (written by the bootstrap sidecar)  or  BAO_TOKEN
  BAO_TRANSIT_MOUNT     transit (default)      BAO_KEY_NAME   vaultly (default)
  MASTER_KEY            required for KEY_PROVIDER=local; with openbao it is OPTIONAL and only
                        used to read keys still wrapped the old way
  KEY_CACHE_TTL_SECONDS 60

Migrating an existing install (what was done for this repo's data)
  1. Back up the database (pg_dump).
  2. docker compose up -d openbao openbao-bootstrap      (wait for the app token to appear)
  3. docker compose up -d --build backend                (starts in Hybrid mode: new keys -> OpenBao)
  4. docker compose run --rm --no-deps backend server rewrap
     -> every project key and application key is now wrapped by OpenBao
  5. Verify, then you may delete MASTER_KEY from .env (keep a copy somewhere safe until you are sure).
  `server rewrap` is idempotent and is also how you adopt a new OpenBao key version.

Rotating the OpenBao key
  docker compose exec openbao-bootstrap sh -c \
    'BAO_ADDR=http://openbao:8200 BAO_TOKEN=$(cat /boot/root-token) bao write -f transit/keys/vaultly/rotate'
  docker compose run --rm --no-deps backend server rewrap
  Check: select left(convert_from(encrypted_dek,'LATIN1'),9), count(*) from projects group by 1;
  -> vault:v2:  Old data keeps working throughout (OpenBao still decrypts v1 until you raise
  min_decryption_version).

!! DISASTER WARNINGS (read these) !!
  - After `rewrap`, the OpenBao key is the ONLY thing that can unwrap your project keys. If the
    OpenBao data is lost, every secret in Postgres is permanently unreadable - MASTER_KEY can no
    longer help.
  - OpenBao data lives in the Docker volume `baodata`; its unseal key and root token are in
    volume `baoboot`. `docker compose down -v` DELETES both. Back them up (stop the container
    first):  docker run --rm -v vaultly_baodata:/d -v "$PWD":/b alpine tar czf /b/baodata.tgz -C /d .
              docker run --rm -v vaultly_baoboot:/d -v "$PWD":/b alpine tar czf /b/baoboot.tgz -C /d .
    Store those archives somewhere safe and separate from the database backups.
  - The single unseal key + root token on a Docker volume is a DEVELOPMENT convenience. In
    production use auto-unseal (cloud KMS/HSM) or split Shamir shares between people, run OpenBao
    with TLS and a multi-node raft cluster, and revoke the root token.

PART 2 - PERSONAL-DATA (PII) ENCRYPTION
---------------------------------------
Goal: a stolen database (or backup, or Kafka log) reveals no names or email addresses.

Technique: application-level field encryption + a blind index
  Seal(field, value)  AES-256-GCM, random nonce, the FIELD NAME is bound as additional data, so a
                      ciphertext cannot be pasted into another column. Stored as "enc:v1:<base64>".
  Index(value)        HMAC-SHA256 with a separate secret key over lower(trim(value)). Equal emails
                      give equal indexes, so you can look a user up and enforce uniqueness WITHOUT
                      storing the email. A plain hash would be brute-forceable; the keyed HMAC is not.
  Keys: two random keys ("pii-enc", "pii-index") created on first start and stored in app_keys,
        wrapped by the KeyProvider (so OpenBao protects them too).

What is encrypted
  users.email_enc / users.name_enc (+ users.email_hash blind index; the old plaintext columns are NULL)
  invites.email_enc (+ email_hash)
  "who did it" labels that contain an email: secrets.updated_by, secret_versions.actor,
     service_tokens.created_by, invites.invited_by, dynamic_leases.created_by
  audit_logs.actor_label and audit_logs.resource (member events) - and the same fields inside the
     Kafka messages, so emails are not kept in the broker's log either
  Existing plaintext rows are encrypted automatically at startup (Backfill; safe to re-run).

WHAT IS ENCRYPTED, AND WHY  (the field policy, internal/pii sealedFields)
  Rule: encrypt what is personal data about people or would help an attacker against a customer's systems.
  Leave readable the labels a team browses and the database orders by. Encrypting those too adds cost
  (no database sorting or filtering) and protects almost nothing.

  ENCRYPTED (AES-256-GCM, the field name is bound into the ciphertext so a value copied to another column
  does not open):
    users: email, name (plus a blind index so login can find an email)
    orgs.name                   workspaces default to "<person>'s workspace"
    secrets: key name, comment  what a secret is for ("STRIPE_LIVE_KEY", "rotate with 1Password item X")
    secret values               separate layer: per-project keys wrapped by OpenBao (see above)
    service_tokens: token prefix (start of the credential), IP allowlist (network addresses)
    personal_tokens: token prefix
    webhooks.url                Slack/Discord-style URLs contain a token
    webhook_deliveries.error, integrations.last_error, dynamic_leases.revoke_error   messages quote hosts and URLs
    audit_logs: actor (emails), resource, IP address; also inside the Kafka messages
    app_keys, integration/dynamic configs (credentials), invitation emails

  READABLE:
    project, environment and folder names, tags, token names, webhook names and event lists, integration and
    dynamic-secret names, invitation and per-environment roles, audit metadata and action names, plus ids,
    timestamps, version numbers, flags and counts.
  Someone with a database dump can see how a team is organised (projects, environments, folders, tag names)
  and how active it is. They cannot see people, secret values, what any secret is called, where tokens may
  connect from, or webhook endpoints.

  Moving a field either way is one line in sealedFields; on the next start the conversion (Backfill) seals or
  unseals the existing rows. Reads accept both forms, so nothing breaks mid-way.

  Lookups the database still does on sealed or readable data use keyed hashes (HMAC with the index key, per field):
    secrets.lookup_hash / path_hash   unique (environment, folder, key); the key name is sealed
    environments.slug_hash, member_env_roles.env_slug_hash, dynamic_configs.name_hash
  A hash reveals only "these two values are equal". Secret search (which looks into sealed key names and
  comments) and folder listing run in the application after decrypting one environment's rows.
  Arrays and JSON columns (tags, events, allowed_cidrs, env_roles, audit metadata) are text columns since
  migration 004; the value is sealed or plain JSON as the policy says.

  A common question: "should secret values be encrypted a second time?" No. A second layer with a key the
  same server holds protects against nothing the first layer does not (an attacker with the database alone
  sees ciphertext; an attacker inside the running server has both keys). Spend effort on OpenBao hardening
  (TLS, auto-unseal, separate host), key rotation (`server rewrap`), least-privilege tokens and audit review.

How the code uses it
  user/service.go    Register stores sealed values; Login looks up by Index(email), then bcrypt;
                     IDByEmail / EmailExists use the blind index
  audit.Service      seals before Kafka and before INSERT; opens before notifying subscribers
  pii.Backfill       idempotent startup migration, batched
  The HTTP API and the React app are unchanged: they still receive decrypted values.

Trade-offs and limits
  - No SQL searching by email substring or name (only exact match via the index). The UI filters
    in the browser after decryption.
  - Decrypting lists costs CPU per row (negligible at this scale; paginate for large tenants).
  - The JWT access token still contains the user's email (it is short-lived and only in memory).
  - Emails also appear in outgoing invitation emails and in webhook payloads (actor field) by design.
  - Rotating the PII keys (re-encrypting every row) is not implemented; only the wrapping of those
    keys rotates via `server rewrap`.
  - If app_keys rows are lost, all sealed fields become unreadable. They are included in normal
    database backups; they cannot be unwrapped without OpenBao.

Verification that exists
  Unit tests (internal/pii, internal/crypto) + a live test against a real OpenBao + 11 end-to-end
  checks, including: a full pg_dump contains neither tester's email address, login works with
  different letter-case (blind index), the API still returns decrypted values.
